From packages/mcp-server/src/tools.ts (resolve_approval logic, lines 547-649):
The approval resolution logic:
1. Fetch pending item by id
2. If action='reject': UPDATE status='rejected', resolved_at=now
3. If action='approve'/'edit': parse metadata JSON as { fact: ExtractedFact, merge_candidate_ids?: string[] }
4. If merge_candidate_ids exist: reassign observations + relationships from secondary entities to primary, delete secondary entities
5. Call rememberEntity() to write fact to knowledge graph (upserts entity, adds observation, inserts FTS + embedding)
6. UPDATE status='approved', resolved_at=now

IMPORTANT: The API server cannot call rememberEntity() directly because it imports from mcp-server and requires embedText/Ollama. Instead, the API server should replicate the DB write logic inline (entity upsert, observation insert, FTS insert) WITHOUT embedding — set needs_embedding=1 so the MCP server's startup sweep handles it.

4. GET `/` — list pending approvals:
   - Query: `SELECT * FROM approval_queue WHERE status = 'pending' ORDER BY created_at DESC LIMIT 50`
   - Parse metadata JSON on each item before returning: `items.map(item => ({ ...item, metadata: item.metadata ? JSON.parse(item.metadata as string) : null }))`
   - Return `c.json({ items })`

5. PATCH `/:id` with `zValidator('json', resolveSchema)`:
   - Extract `id` from `c.req.param()`, `data` from `c.req.valid('json')`
   - Fetch item: `SELECT id, item_type, metadata, status FROM approval_queue WHERE id = ?`
   - If not found: return `c.json({ error: 'Approval item not found' }, 404)`
   - If `item.status !== 'pending'`: return `c.json({ error: 'Item already resolved' }, 409)`
   - `const now = new Date().toISOString()`

   **Reject path:**
   - If `data.status === 'rejected'`: `UPDATE approval_queue SET status = 'rejected', resolved_at = ? WHERE id = ?`
   - Return `c.json({ status: 'rejected', id })`

   **Approve path:**
   - Parse metadata: `const meta = JSON.parse(item.metadata) as { fact: ExtractedFact, merge_candidate_ids?: string[] }`
   - Determine observation text: `data.edited_content ?? meta.fact.observation`

   **Merge candidate handling** (replicate MCP server logic exactly):
   - If `meta.merge_candidate_ids?.length > 0`:
     - Find primary entity: `SELECT id FROM entities WHERE name = ? AND type = ?` using `meta.fact.entity_name`, `meta.fact.entity_type`
     - For each secondary ID in `merge_candidate_ids`:
       - `UPDATE observations SET entity_id = ? WHERE entity_id = ?` (primary <- secondary)
       - `UPDATE relationships SET from_id = ? WHERE from_id = ?` (primary <- secondary)
       - `UPDATE relationships SET to_id = ? WHERE to_id = ?` (primary <- secondary)
       - `DELETE FROM entities WHERE id = ?` (delete secondary)

   **Write fact to knowledge graph** (inline, no embedText call):
   - Check existing entity: `SELECT id FROM entities WHERE name = ? AND type = ?`
   - If not exists: `INSERT INTO entities (id, name, type, summary, metadata, session_id, agent_id, source_type, confidence, created_at, updated_at) VALUES (?, ?, ?, NULL, '{}', 'api-server', 'api-server', 'consolidation', ?, ?, ?)`
   - Insert observation: `INSERT INTO observations (id, entity_id, content, metadata, session_id, agent_id, source_type, confidence, created_at, needs_embedding) VALUES (?, ?, ?, '{}', 'api-server', 'api-server', 'consolidation', ?, ?, 1)`
   - Note: `needs_embedding = 1` — the MCP server's startup re-embed sweep will handle embedding later
   - Insert FTS: `INSERT INTO fts_observations (content, observation_id) VALUES (?, ?)`
   - Handle related entities from `meta.fact.related_entities`: for each, upsert the target entity and insert relationship with `nanoid()` IDs

   **Finalize:**
   - `UPDATE approval_queue SET status = 'approved', resolved_at = ? WHERE id = ?`
   - Return `c.json({ status: 'approved', id, entity: meta.fact.entity_name })`

   **Wrap the entire approve path in a transaction** using `db.transaction(...)()` for atomicity.
