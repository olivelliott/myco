**Walk-up resolution design:** The `selectProjectForPath` statement uses `WHERE ? LIKE directory_path || '%'` which matches any input path that starts with a registered directory_path. `ORDER BY LENGTH(directory_path) DESC LIMIT 1` ensures the longest (nearest ancestor) match wins. For example, if `/a/b` and `/a` are both registered, querying `/a/b/c/d` matches both but `/a/b` is returned because it has the longer directory_path.

**Important:** All directory_path values MUST be stored without a trailing slash. The LIKE pattern `directory_path || '%'` means `/a/b` matches `/a/b`, `/a/b/c`, `/a/b/anything`. It would also match `/a/bx` -- to prevent false positives, callers should normalize paths (resolve symlinks, remove trailing slashes). This is acceptable for Phase 24; Phase 25/26 will normalize at the caller layer.

**Important edge case note:** The LIKE pattern `directory_path || '%'` WILL match `/a/bx` when `/a/b` is registered because `/a/bx` starts with `/a/b`. To make this test pass, add a path separator boundary to the query. Update `selectProjectForPath` in statements.ts to:

```sql
SELECT id, project_name, directory_path, created_at
FROM project_paths
WHERE (? = directory_path OR ? LIKE directory_path || '/%')
ORDER BY LENGTH(directory_path) DESC
LIMIT 1
```

This query uses two conditions:
- `? = directory_path` -- exact match (e.g., `/a/b` matches `/a/b`)
- `? LIKE directory_path || '/%'` -- subdirectory match with slash boundary (e.g., `/a/b/c` matches `/a/b/` prefix but `/a/bx` does NOT match `/a/b/`)

The parameter `?` must be bound twice. Update the statement to use a named parameter `$path`:

```typescript
selectProjectForPath: db.prepare(
  `SELECT id, project_name, directory_path, created_at
   FROM project_paths
   WHERE ($path = directory_path OR $path LIKE directory_path || '/%')
   ORDER BY LENGTH(directory_path) DESC
   LIMIT 1`
),
```
